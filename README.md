# Data Platform: рыночный коридор ставок и прогноз цены перевозки

Решение задания DE. Пайплайн забирает сделки из операционной БД `deals_bigdata`, очищает их и приводит к рублям, строит витрину «карточка маршрута» с рыночным коридором ставок и обучает модель прогноза ставки с пакетным скорингом плановых заявок.

Всё поднимается одной командой:

```bash
docker-compose up
```

## Быстрый старт

Нужен только Docker с Compose v2. Файл `.env` не обязателен: без него действуют значения по умолчанию из `docker-compose.yml` (перечень переменных — в `.env.example`).

```bash
docker-compose up          # или: docker compose up
```

Что происходит:

1. `postgres` (PostgreSQL 17) при первом старте создаёт источник `deals_bigdata` из `sql/source/schema.sql` и `synthetic.sql` (300 000 сделок), пустую базу `dwh` и техническую роль `ul_etl` (только чтение источника, владелец DWH).
2. `app` дожидается готовности БД и выполняет `python -m pipeline run-all`: миграции DWH → extract → transform → витрина → обучение → скоринг. После завершения контейнер останавливается с кодом 0, PostgreSQL продолжает работать.

Первый запуск занимает несколько минут: сборка образа, генерация синтетики и сам пайплайн (около минуты-двух).

Подключение к результату:

```bash
docker compose exec postgres psql -U ul_etl -d dwh
```

С хоста PostgreSQL доступен на `localhost:5432` (пользователь и пароль `ul_etl`). Если порт занят, задайте другой: `POSTGRES_PORT=5433 docker-compose up`.

Полный сброс: `docker compose down -v`.

## Архитектура

```
deals_bigdata (источник, read-only)
        │  extract: окно по prices.updated_at, COPY
        ▼
  raw    копия таблиц источника как есть (prices, price_body_types, price_dates, справочники)
        │  transform: SQL, по транзакции на календарный месяц
        ▼
  core   fact_price (валидные сделки, price_rub)      dq.dq_quarantine_prices (брак + причина)
         fact_price_body_group, fact_price_month      сверка: прочитано = загружено + карантин
         dim_city, exchange_rate
        │                                   │
        ▼                                   ▼
  mart.mart_route_card              ml: признаки → CatBoost → mart.ml_price_predictions
  (рыночный коридор по месяцам)                              mart.ml_model_metrics
```

Обе базы живут в одном экземпляре PostgreSQL, но пайплайн обращается к ним как к двум независимым подключениям (`SOURCE_DB_*`, `DWH_DB_*`), поэтому источник можно вынести на другой хост без правок кода.

| Схема DWH | Назначение |
|---|---|
| `raw` | Сырые копии таблиц источника за загруженные окна |
| `core` | Очищенные сделки в рублях, связи «сделка — группа кузова» и «сделка — месяц», справочники |
| `dq` | Карантин невалидных записей с кодом причины и исходной строкой в `jsonb` |
| `mart` | Карточка маршрута, прогнозы, метрики модели, представления для аналитиков |
| `etl` | `run_log` — журнал шагов: окно, статус, длительность, статистика |

Трансформации написаны на SQL (`sql/transforms/`), Python отвечает за порядок шагов, транзакции, окна и журнал. Логи структурированные (JSON), секреты в них не попадают.

## Обоснование стека

**PostgreSQL 17** — стек, заданный в задании, и его достаточно: на 300 тыс. сделок вся витрина пересчитывается за секунды, `percentile_cont` даёт точные квартили, `INSERT … ON CONFLICT` и транзакции дают идемпотентность без дополнительных инструментов.

**SQL + Python (psycopg 3, без ORM и без dbt).** Бизнес-правила читаются в SQL-файлах в порядке выполнения; данные между базами идут потоково через `COPY`, без загрузки в память. dbt для шести SQL-файлов добавил бы инфраструктуры больше, чем пользы.

**Оркестратор.** Базовый запуск — CLI `python -m pipeline`, чтобы `docker-compose up` не требовал Airflow. Каждый шаг — идемпотентная команда с параметрами окна, поэтому DAG в Airflow (бонус) лишь вызывает те же функции.

**ML-модель — CatBoost.** Рекомендация R&D-отчёта, подтверждённая на этих данных: лучшие R² и MAPE из трёх семейств, категориальные признаки (города, регионы, кузов) обрабатываются нативно. Ridge и DecisionTree обучаются как baseline — только ради сравнения метрик.

## ETL: окно загрузки, качество данных, идемпотентность

### Почему окно — по `updated_at`, а не по дате погрузки

Все шаги параметризуются окном `--start / --end`; сделка попадает в окно по `prices.updated_at`. Это осознанный выбор:

1. **Сделки появляются задолго до погрузки.** 91,8 % сделок созданы раньше даты погрузки, у 19,2 % погрузка приходится на более поздний месяц, чем создание (опережение до 110 дней). При окне по дате погрузки ежедневный запуск «за вчера» не увидел бы заявку, созданную вчера с погрузкой через две недели.
2. **Плановые заявки — обязательная часть задания.** Скоринг нужен для заявок с `loading_date > as_of` (в источнике их 6 003). Окно по дате погрузки «до сегодня» их не содержит по определению.
3. **Правки задним числом.** В реальном источнике цена или статус меняются и после погрузки. Окно по `updated_at` подхватывает такую правку автоматически в день изменения; при окне по дате погрузки пришлось бы угадывать, какой период перезагружать.
4. **Многомесячные заявки.** У 15 085 сделок даты в `price_dates` покрывают несколько месяцев. `loading_date` — только начало и не определяет, к каким месяцам рынка относится сделка.

Цена решения: пайплайн полагается на дисциплину источника — см. [допущения](#допущения-и-ограничения).

### Правила качества данных

Каждая сделка окна попадает либо в `core.fact_price`, либо в карантин; запись с несколькими нарушениями получает строку на каждую причину.

| Код причины | Правило |
|---|---|
| `REQUIRED_FIELD_NULL` | не заполнено обязательное поле |
| `PRICE_NON_POSITIVE` | `price <= 0` |
| `PRICE_RUB_BELOW_MIN` | рублёвая ставка `price <= 1000` |
| `DISTANCE_NON_POSITIVE` | `distance <= 0` |
| `WEIGHT_NEGATIVE`, `VOLUME_NEGATIVE` | отрицательный вес или объём |
| `LOADING_CITY_UNKNOWN`, `UNLOADING_CITY_UNKNOWN` | города нет в справочнике |
| `CURRENCY_UNKNOWN` | валюта не RUB / USD / EUR |
| `FX_RATE_DATE_MISSING` | валютная сделка без `nearest_rate_date` |
| `FX_RATE_NOT_FOUND` | нет курса на `nearest_rate_date` |

Остальные преобразования:

- **Валюта.** `price_rub = price × курс` строго на `nearest_rate_date`; для рублёвых сделок курс не нужен, пустая дата курса — не ошибка.
- **Города.** Дубли по `gc_id` схлопываются до записи с минимальным `id`; регион выделяется из полного названия.
- **Группы кузова.** Коды из `price_body_types` (при отсутствии — `prices.body_type`) приводятся к группам «Тент», «Рефрижератор», «Изотерм», «Борт», «Прочие», «Не указан». Сделка с несколькими кузовами учитывается в каждой своей группе один раз.
- **Категории веса и объёма.** Пропуски заполняются по границам из задания (`core.fn_weight_category`, `core.fn_volume_category`).
- **`outlier_mark`** используется как входной флаг и не пересчитывается.

### Результат на эталонном датасете

| Показатель | Значение |
|---|---|
| Прочитано сделок | 300 000 |
| Загружено в `core.fact_price` | 299 797 |
| В карантине | 203 (164 — `PRICE_NON_POSITIVE`, 39 — `FX_RATE_DATE_MISSING`) |

После каждого окна выполняется сверка «прочитано = загружено + карантин»; расхождение откатывает транзакцию.

### Идемпотентность

- `raw`: строки окна удаляются и вставляются заново (DELETE + INSERT по ключу сделки).
- `core`: `INSERT … ON CONFLICT (price_id) DO UPDATE`; связи с кузовами и месяцами пересобираются для сделок окна.
- Карантин: записи сделок окна пересоздаются; исправленная в источнике сделка покидает карантин и попадает в core, и наоборот.
- Период длиннее месяца делится на календарные месяцы — по транзакции на месяц, сбой откатывает только текущий.

Повторный запуск за тот же период не меняет ни количество строк, ни суммы — это проверяют тесты `tests/test_idempotency.py`.

## Витрина «карточка маршрута»

`mart.mart_route_card`, зерно: **месяц × город погрузки × город выгрузки × группа кузова × весовая категория**. Эталонный запрос — `sql/transforms/mart/10_route_card.sql`, отбор рыночных сделок — представление `core.v_market_base`.

В расчёт входят только фактические сделки (`is_fact`), не комплексные, без `outlier_mark`, с датой из `price_dates` не позже `as_of`. Месяц берётся по `price_dates`, а не по `loading_date`.

| Группа | Поля |
|---|---|
| Коридор за рейс, руб. без НДС | `p25_trip`, `median_trip`, `p75_trip`, `avg_trip` |
| Коридор за километр | `p25_km`, `median_km`, `p75_km` |
| Доказательная база | `trips_count`, `carriers_count` (уникальные организации с `price_type IN (3, 9)`), `cv_rate` |
| Динамика | `mom_pct`, `yoy_pct` — к медиане предыдущего календарного месяца и того же месяца год назад |
| Надёжность | `reliability_level`, `last_price_date`, `freshness_days` |

`reliability_level`: `HIGH` — не менее 30 рейсов, не менее 5 перевозчиков и свежесть не более 30 дней от `as_of`; `MEDIUM` — не менее 10 рейсов; иначе `LOW_DATA`.

«Сегодня» для витрины — `AS_OF` (по умолчанию `2026-10-26`), а не системная дата. Задать `as_of` позже последнего дня данных нельзя: команда завершится ошибкой.

Итог на эталонных данных: 203 644 ячейки за 37 месяцев; `HIGH` — 10, `MEDIUM` — 924, `LOW_DATA` — 202 710. Синтетика равномерно размазана по 40 городам, поэтому большинство ячеек редкие — именно этот случай и закрывает `reliability_level`.

По умолчанию витрина пересчитывается целиком (несколько секунд) и всегда согласована с core. Режим `marts --incremental` пересчитывает только последние `MART_LOOKBACK_MONTHS` месяцев и пропущенные — он оставлен для больших объёмов.

## ML: прогноз ставки

**Цель** — `price_rub` фактической сделки. **Разбиение хронологическое относительно `as_of`:**

| Выборка | Период (`as_of = 2026-10-26`) | Строк |
|---|---|---|
| train | 2026-07-26 … 2026-10-04 (3 месяца до test) | 24 226 |
| test | 2026-10-05 … 2026-10-26 (последние 3 недели) | 12 808 |
| future | `loading_date > 2026-10-26` | 4 891 |

Хвост train используется для ранней остановки CatBoost, после чего модель переобучается на всём train с найденным числом итераций.

**Признаки:** расстояние, вес, объём, координаты городов, регионы и коды городов, группа и тип кузова, категории веса и объёма, тип записи, календарные признаки с циклическим кодированием. Таргет очищается по `outlier_mark`, но сам флаг признаком не является. Список запрещённых признаков (цена и её производные, `price_group_stats`, `outlier_mark`) зафиксирован в `ml/features.py` и проверяется тестом.

### Метрики на test

| Модель | R² | MAPE, % | RMSE, руб. | MAE, руб. |
|---|---|---|---|---|
| **CatBoost** (основная) | **0,925** | **14,95** | **52 235** | **26 867** |
| DecisionTree | 0,907 | 16,02 | 58 347 | 30 304 |
| Ridge | 0,842 | 49,37 | 75 960 | 47 840 |

Порядок моделей и уровень качества соответствуют ориентирам R&D-отчёта (CatBoost ≈ 0,93 / 13 %). Метрики воспроизводятся точно при фиксированном `RANDOM_SEED` в одном и том же образе; на другой платформе или версии библиотек возможны расхождения в сотых долях. Они сохраняются в `mart.ml_model_metrics` и в отчёте `metrics.json` (том `artifacts`) вместе с параметрами и важностью признаков:

```bash
docker compose run --rm app cat /app/artifacts/metrics.json
```

Вывод отчёта о поведении R² на узких сегментах подтверждается представлением `mart.v_model_error_by_segment`: для тентов на плече 1000+ км R² = 0,90 при MAPE 14 %, а на плече до 300 км R² падает до 0,35.

### Пакетный скоринг

В `mart.ml_price_predictions` пишется только основная модель: 13 078 строк test (с фактом и ошибкой, включая помеченные выбросы — флаг сохранён в строке) и 4 891 плановая заявка. Для плановых заявок `actual_price_rub`, `abs_error_rub` и `ape_pct` всегда `NULL`, даже если в источнике поле `price` заполнено; это закреплено ограничением `CHECK` в таблице. Перезапись — DELETE + COPY в одной транзакции.

Представление `mart.v_fact_vs_forecast` соединяет прогноз с последним доступным рыночным коридором маршрута и подсвечивает рейсы, закрытые выше прогноза на 15 % или выше `p75` рынка.

## Повторный запуск и backfill

Команды выполняются в контейнере приложения:

```bash
# перезагрузить сделки, изменённые в сентябре 2026, и пересчитать витрину
docker compose run --rm app python -m pipeline etl --start 2026-09-01 --end 2026-09-30
docker compose run --rm app python -m pipeline marts

# переобучить модель и пересчитать прогнозы
docker compose run --rm app python -m pipeline ml run

# весь пайплайн заново за всю историю источника
docker compose run --rm app python -m pipeline run-all
```

| Команда | Действие |
|---|---|
| `init-db` | миграции DWH (идемпотентны) |
| `extract --start --end` | источник → `raw` за окно |
| `transform --start --end` | `raw` → `core` + карантин за окно |
| `etl --start --end` | `extract` + `transform` |
| `marts [--as-of] [--incremental]` | пересчёт витрины |
| `ml train` / `ml score` / `ml run` | обучение, скоринг, оба шага |
| `run-all` | всё по порядку |

Окно задаётся по `updated_at`; без `--start / --end` берётся вся история. Дата снимка: `--as-of`, иначе `AS_OF` из окружения, иначе последний день данных. Журнал запусков — `etl.run_log`.

## SQL для проверки результата

```sql
-- 1. Сверка слоёв и причины карантина
SELECT (SELECT count(*) FROM raw.prices)                              AS raw_rows,
       (SELECT count(*) FROM core.fact_price)                         AS core_rows,
       (SELECT count(DISTINCT price_id) FROM dq.dq_quarantine_prices) AS quarantined;
SELECT * FROM dq.v_quarantine_summary;

-- 2. Карточка маршрута: самые надёжные ячейки последнего месяца
SELECT month, loading_city, unloading_city, body_group, weight_category,
       p25_trip, median_trip, p75_trip, median_km,
       trips_count, carriers_count, cv_rate, mom_pct, yoy_pct, reliability_level
FROM mart.mart_route_card
WHERE reliability_level = 'HIGH'
ORDER BY month DESC, trips_count DESC
LIMIT 10;

-- 3. История одного маршрута (Москва → Ростов-на-Дону, тент, FTL)
SELECT month, median_trip, p25_trip, p75_trip, trips_count, mom_pct, yoy_pct, reliability_level
FROM mart.mart_route_card
WHERE loading_city = 'Москва' AND unloading_city = 'Ростов-на-Дону'
  AND body_group = 'Тент' AND weight_category = 'FTL'
ORDER BY month DESC;

-- 4. Последний доступный коридор по каждой ячейке сети
SELECT * FROM mart.v_route_card_latest LIMIT 20;

-- 5. Метрики моделей
SELECT model_name, r2, mape_pct, rmse_rub, mae_rub, n_rows
FROM mart.ml_model_metrics ORDER BY r2 DESC;

-- 6. Прогнозы: у плановых заявок факта нет
SELECT split, count(*) AS rows_cnt, count(actual_price_rub) AS with_actual,
       min(loading_date) AS date_from, max(loading_date) AS date_to
FROM mart.ml_price_predictions GROUP BY split;

-- 7. Рейсы, закрытые выше прогноза и выше рыночного p75
SELECT price_id, loading_date, body_group, actual_price_rub, predicted_price_rub, p75_trip, ape_pct
FROM mart.v_fact_vs_forecast
WHERE above_forecast_15pct AND above_market_p75
ORDER BY ape_pct DESC LIMIT 20;

-- 8. Качество модели по сегментам
SELECT * FROM mart.v_model_error_by_segment ORDER BY body_group, distance_band;

-- 9. Журнал шагов
SELECT step, status, count(*) AS runs, max(finished_at) AS last_finished
FROM etl.run_log GROUP BY step, status ORDER BY step;
```

|---|---|---|---|---|---|---|---|---|---|---|
| 2026-10 | Москва → Ростов-на-Дону | Тент | FTL | 112 795,68 | 126 991,51 | 145 143,74 | 112 | 39 | 0,47 | 17,69 |
| 2026-10 | Москва → Ростов-на-Дону | Рефрижератор | FTL | 151 386,37 | 163 418,54 | 180 761,23 | 49 | 14 | 5,17 | 9,98 |

## Тесты

Тесты интеграционные и работают поверх загруженного DWH, поэтому запускаются после `docker-compose up`:

```bash
docker compose run --rm app python -m pytest
```

Что покрыто: правила DQ на специально подготовленных строках, границы категорий, сверка окна, конвертация валют, дедупликация городов и групп кузова, идемпотентность повторных запусков, замена версии сделки при изменении в источнике, сверка витрины с независимым эталонным запросом, правила MoM / YoY и `reliability_level`, отсутствие запрещённых признаков, границы train / test, `NULL` в факте плановых заявок. Тесты ClickHouse включаются переменной `CLICKHOUSE_TESTS=1`.

## Бонус: ClickHouse и Airflow

Бонусные сервисы вынесены в профиль и не мешают базовому запуску:

```bash
docker compose --profile bonus_task up
```

**ClickHouse** (`localhost:8123`). После основного пайплайна `clickhouse-sync` переносит аналитический слой:

- `market_base` — рыночные сделки, `ReplacingMergeTree`, партиции по месяцу, ключ сортировки начинается с маршрута;
- `mart_route_card` — та же карточка маршрута, рассчитанная средствами ClickHouse, `MergeTree`;
- данные читаются из PostgreSQL напрямую через именованную коллекцию; обновление — подготовка во временной таблице и атомарная замена партиций, поэтому повтор идемпотентен;
- после синхронизации витрина сверяется с PostgreSQL.

Ручной запуск: `python -m pipeline clickhouse-sync [--start … --end …]`.

**Airflow 3** (`http://localhost:8080`, режим standalone без авторизации — только для локальной демонстрации). DAG создаются на паузе:

| DAG | Расписание | Назначение |
|---|---|---|
| `ul_platform_backfill` | вручную | полный прогон или период из параметров |
| `ul_platform_daily` | `@daily` | инкремент за день: extract, transform, витрина, обучение, скоринг |
| `ul_platform_marts_full` | `@weekly` | полный пересчёт витрины |
| `ul_platform_clickhouse_sync` | вручную | синхронизация ClickHouse |

Дата снимка в DAG берётся из `AS_OF` (или параметра запуска) и не может быть позже последнего дня данных, поэтому запуск на замороженном датасете не сдвигает «сегодня» на системную дату.


## Допущения и ограничения

1. **`outlier_mark` за последний день снимка.** Сделки, созданные 2026-10-26, ещё не прошли ночную разметку аномалий: из 5 931 такой сделки помечены 3 (0,05 %) против 1,72 % в остальных данных. Флаг в решении не пересчитывается, поэтому неразмеченные выбросы последнего дня входят и в витрину за октябрь 2026, и в test-выборку модели. Это ограничение исходных данных; метрики и коридор последнего месяца могут быть слегка смещены.
2. **Инкремент опирается на `updated_at`.** Предполагается, что источник обновляет `prices.updated_at` при любом изменении сделки, включая её строки в `price_body_types` и `price_dates`. Сделки с пустым `updated_at` не попадут ни в одно окно — о них пишется предупреждение в лог. В источнике нет индекса по `updated_at`, поэтому окно читается последовательным сканированием; для боевого объёма индекс нужно добавить.
3. **Физические удаления в источнике не отслеживаются.** Удалённая сделка остаётся в `raw` и `core`. Решение для продакшна — мягкое удаление в источнике или периодическая сверка ключей.
4. **Плановые заявки с браком не скорятся.** Три будущие заявки с нулевой ценой или без даты курса уходят в карантин по общим правилам и не получают прогноза.
5. **Группа кузова в ML** определяется по основному `prices.body_type`; в витрине сделка с несколькими кузовами учитывается в каждой группе.
6. **`reliability_level = HIGH` возможен только для последних месяцев** — это следствие условия свежести «не более 30 дней от `as_of`».
7. **Пароли по умолчанию** в `docker-compose.yml` нужны только для запуска без ручной настройки; для любого другого окружения они задаются через `.env`. В коде паролей нет, при отсутствии переменной приложение не стартует.
